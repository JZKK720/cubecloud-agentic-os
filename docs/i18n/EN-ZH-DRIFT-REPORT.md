| Locale | Files | Missing files | Missing keys (within present files) |
|---|---|---|---|
| en | 24 | — | (source) |
| zh-CN | 24 | none | 0 |

| ja | 23 | **kanban.ts** | 0 |
| pt-BR | 23 | **kanban.ts** | 0 |

At runtime, the 4 locales missing `kanban.ts` fall back to `en` for kanban strings. This may be intentional (kanban screen not yet translated), but it should be a **deliberate** decision, not silent drift. Two options:

1. **Decide "kanban not translated in {es,id,ja,pt-BR}".** Document it in `agent-desktop/src/shared/i18n/locales/<lang>/README.md` (one line) and add an explicit `// INTENTIONALLY_FALLS_BACK_TO_EN` marker in `index.ts` so `check-i18n-coverage.cjs --strict` accepts it.
2. **Translate kanban.ts into the 4 missing locales.** This is the right long-term answer; copy `en/kanban.ts` and translate the values.

The current i18n test (`agent-desktop/src/shared/i18n/index.test.ts`) does not assert parity. Adding that assertion would have caught this in CI.

## D. Where mojibake **was** seen (and is not actually a file issue)

The PowerShell session surfaces these sequences in the **console output** during the build:

| Sequence | Real meaning |
|---|---|
| `馃寪` (and similar) | i18next's sponsorship banner; rendered as 馃寪 by the default Windows code page 437 when the terminal doesn't claim UTF-8. Set `chcp 65001` at the start of the session. |
| `鈥` | an em-dash (`—`) read as CP1252 |
| `鎷掔粷璁块棶銆` | "Access denied" in Chinese, encoded as UTF-8 but read as CP1252 |
| `锘縜` | UTF-8 BOM, read as garbled text |

**The on-disk files are clean UTF-8** (verified by `scripts/check-mojibake.cjs`, 802 files scanned). All these are **terminal rendering** issues, not file corruption. Fix in the terminal, not in the files.
