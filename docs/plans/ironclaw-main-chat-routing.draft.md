# Plan: Route the main Chat screen to IronClaw (Fix F)

> **Status: DRAFT — not implemented. Awaiting design decision + owner approval.**
> Generated by the runtime-connection audit. This is a `plan.prompt.md`-shaped
> proposal for the bigger IronClaw feature work. The smaller fixes (E, G) are
> already applied; this one needs a design call first.

## Problem

The main Chat screen (`sendMessage` → `sendMessageViaApi` in
`agent-desktop/src/main/hermes.ts`) cannot route to IronClaw. Even after
attaching IronClaw via Settings → Connection → Remote (green dot, "reachable"),
typing in the main Chat screen hits `sendMessageViaApi`, which uses
`getApiUrl()` (the Hermes/remote URL) and treats the runtime as Hermes.

`diagnoseRemoteConnection` (`hermes.ts:239`) *does* detect IronClaw (probes
`/api/health`, checks body for `"channel":"gateway"`, caches as
`runtimeKind = "ironclaw"`) — but there is **no `runtimeKind === "ironclaw"`
branch** in `sendMessageViaApi`. Only `openclaw` gets special treatment.

The only path that actually chats through IronClaw today is the dedicated
Sandbox Tasks screen (`SandboxTasks.tsx` → `ironclaw-dispatch` IPC →
`dispatchSandboxTask` in `ironclaw-sandbox.ts`).

## Design decision needed: where does the IronClaw gateway URL + token come from?

Three options. Pick one before implementing.

### Option 1 (recommended): Reuse the saved Model card

The Settings → Remote attach flow already saves a Model card with a URL +
stored credential. `sendMessageViaApi` could read the active Model card's
`baseUrl` + `apiKey` when `runtimeKind === "ironclaw"`.

- **Pro:** minimal new config surface; reuses existing storage + UI.
- **Pro:** the green-dot health probe already validates this URL.
- **Con:** the Model card's `apiKey` field is currently Hermes-shaped
  (`API_SERVER_KEY` / remote bearer). Need to confirm it can hold an
  IronClaw `GATEWAY_AUTH_TOKEN`.
- **Con:** `sendMessageViaApi` currently calls `getApiUrl()` which reads
  `getConnectionConfig().remoteUrl`. Need a parallel path for IronClaw.

### Option 2: New `ironclaw` section in `getConnectionConfig` (desktop.json)

Add `ironclaw: { url, token }` to `desktop.json`'s connection config.

- **Pro:** explicit, separate from Hermes config.
- **Con:** adds config surface; needs a new Settings UI section or a
  reuse of the existing Remote panel with a runtime-lane toggle.

### Option 3: Defer — Sandbox Tasks is the IronClaw chat path

Don't route the main Chat screen to IronClaw. Document that IronClaw chat
lives in the Sandbox Tasks screen. The Settings → Remote attach form's
green dot is for health monitoring only, not chat routing.

- **Pro:** zero code change; honest about the current architecture.
- **Con:** the Settings → Remote "IronClaw" lane is misleading (green dot
  implies chat works). Either fix the UX copy or accept the confusion.

## Proposed implementation (assuming Option 1)

### Task 1: Add `runtimeKind === "ironclaw"` branch in `sendMessageViaApi`

In `agent-desktop/src/main/hermes.ts`, around line 838 (where the `openclaw`
branch lives), add:

```ts
if (runtimeKind === "ironclaw") {
  // IronClaw is OpenAI-compatible: same /v1/chat/completions endpoint,
  // same body shape. Differences: no X-Hermes-Session-Id header, and the
  // gateway URL + bearer token come from the saved Model card (not
  // getApiUrl() / getApiServerKey()).
  const ironclawUrl = getActiveIronClawUrl();   // new helper
  const ironclawToken = getActiveIronClawToken(); // new helper
  headers = {
    "Content-Type": "application/json",
    ...(ironclawToken ? { Authorization: `Bearer ${ironclawToken}` } : {}),
  };
  // apiUrl is used by startPreparedRequest to build the /v1/chat/completions URL
  apiUrl = ironclawUrl.replace(/\/$/, "");
}
```

### Task 2: Add `getActiveIronClawUrl` / `getActiveIronClawToken` helpers

These read the saved Model card for the active IronClaw runtime. Where do
Model cards live? Check `agent-desktop/src/main/models.ts` /
`config.ts` for the saved-model storage shape. The helpers return `""` if
no IronClaw Model card is active (in which case the chat falls back to
the Hermes path or errors with a friendly "No IronClaw gateway attached").

### Task 3: Skip `X-Hermes-Session-Id` for IronClaw

The session-id logic in `finalizePreparedRequest` (`hermes.ts:855-870`)
gates `X-Hermes-Session-Id` on `runtimeKind === "hermes"`. IronClaw is
already excluded (it's `"ironclaw"`, not `"hermes"`), so no change needed
here — but verify the `shouldGenerateSessionId` check
(`runtimeKind === "openclaw" || "Authorization" in headers`) doesn't
generate a spurious `desk-` id for IronClaw. If it does, add
`runtimeKind === "ironclaw"` to the openclaw-style skip.

### Task 4: Test

Add a test in `tests/hermes-api.test.ts` (or a new
`tests/ironclaw-main-chat.test.ts`) that:
- Mocks `getConnectionConfig` to return an IronClaw URL.
- Mocks `diagnoseRemoteConnection` / `getCachedGatewayRuntime` to return
  `"ironclaw"`.
- Asserts `sendMessage` hits `/v1/chat/completions` on the IronClaw URL
  with `Authorization: Bearer <token>` and **no** `X-Hermes-Session-Id`.

### Task 5: UX copy fix

In `Settings.tsx`, the IronClaw Remote attach panel should say "Attach for
health monitoring + Sandbox Tasks chat" until Fix F lands, or "Attach for
chat" after it lands. Don't imply main-Chat routing works until it does.
