## What this release changes

V2.10.79 → V2.10.80-draft is the **Workspace Console P0 + P0.5** slice: the
first implementation of the workspace↔desktop control-console contract
(`docs/plans/2026-10-06-cubecloud-agent-integration-plan.md` row A) and the
EverMind replan P0.5 (`docs/plans/2026-10-06-evermind-memory-harness-replan.md`).

### Workspace Console probe (P0 — contract row A)

- **New module** `src/main/cubecloud-agent-probe.ts`: stateless HTTP probe of
  the AI Workspace server — `GET /health` (required) + opportunistic
  `GET /v1/info` / `GET /v1/stack/status` (optional, older builds 404).
  Never throws; `normalizeWorkspaceOrigin()` accepts loopback-host http
  origins only (the same allow-list class as `isAllowedWebviewUrl`), so a
  stray user-entered remote URL can never be probed as loopback.
- **New IPC channels** in `src/main/index.ts`: `workspace-probe` (health +
  identity) and `workspace-probe-url` (the loopback origin the renderer will
  feed the hardened webview embed in row C — pinned to
  `http://127.0.0.1:6767` until the P5 config center persists an override).
- **Preload bridge** (`src/preload/index.ts` + `index.d.ts`): `workspaceProbe`
  / `workspaceProbeUrl` with a documented `WorkspaceProbeResult` shape.
- **Tools screen card** (`src/renderer/src/screens/Tools/Tools.tsx`): the
  "AI Workspace (cubecloud-agent)" console card — Reachable/Unreachable pill,
  version from `/v1/info` when present, attached-at origin, refresh button.
  Follows the existing Agent-Reach/GBrain panel conventions.

### Raven registry consistency (P0.5)

- **`src/main/runtime-registry.ts`**: the Raven case no longer hardcodes
  `status: "planned"` / `available: false` (which contradicted the catalog's
  `integrationStatus: "optional"`). It now reports a detected-aware
  `ready/available` snapshot with a `scan-raven-gateway` rescan action and an
  install-guide action, mirroring the OpenClaw case's structure.
- **`src/shared/runtime-orchestration.ts`**: `RuntimeProviderActionId` gains

  pin is replaced with the 0.2.x reality and the WebUI (18793) vs gateway
  (8855) port distinction.

### EverCore memory tier lifecycle (P1.5 — contract row H)

- **Supervisor extension** in `src/main/cubecloud-agent-supervisor.ts`:
  `startWorkspaceSupervisor` now ensures the shared EverCore memory tier
  alongside the workspace — config-gated (a disabled `everos` block or no
  wiring at all keeps the tier off), never double-starts an already-running
  sidecar (`memoryTier: "external"`), and delegates readiness to the
  existing `everos-sidecar.ts` manager. Sovereignty rule respected: local
  127.0.0.1:1995 only, operator config untouched, port never published.
- **New status field** `memoryTier: "disabled" | "external" | "starting" |
  "down"` on `WorkspaceSupervisorStatus` (preload `d.ts` updated).
- **Main-process wiring**: the `workspace-supervisor-start` IPC handler
  passes the real everos config loader + sidecar in production.
- **Tools card**: the AI Workspace card gains a "Memory tier (EverCore)"
  row with the four states rendered as pill/hint text.
- Never throws: any tier ensure failure logs to the ring and degrades to
  `down`; the workspace start itself is unaffected.

**Operator decision (2026-10-07): NO EverOS/EverCore integration.**
A follow-up session briefly wired an EverCore memory-tier ensure into
the workspace supervisor (P1.5 — 3 tests, `memoryTier` status field,
Tools-card row) and it passed review, but the operator ruled EverOS
stays a **third-party tool surface** on the Agentic OS (its own Tools
panel, config, sidecar — as today), NOT a shared-memory component of
the workspace attach path. The coupling was fully reverted in the same
branch (supervisor module, tests, preload type, IPC wiring, card row);
the suite is back to 128 files / 1421 tests, P1 intact. The workspace
attach contract therefore has **no EverCore dependency** — coordination
with the AI Workspace is relationship/registry-level only, recorded in
`docs/plans/2026-10-06-workspace-agentic-os-coordination-matrix.md`.

### Persona/skills adoption (P4 — rows R2+R3) + OpenViking probe (R5)

- **New module** `src/main/agent-bundle-compiler.ts`: compiles a desktop
  persona into the canonical cubecloud-agent bundle — a gzipped POSIX tar
  (`config.yaml` with `spec_version: 1` / name / description /
  `executor.type: agent-meow` / harness / model / prompt, optional
  `AGENTS.md` + `instructions:` pointer) — **zero new dependencies**
  (hand-rolled ustar tar + environment-adaptive gzip: `node:zlib` in
  Node/test env, CompressionStream in the Electron renderer; the same
  builder the workspace's own SPA emits). One real tar bug fixed in
  review: the size/mtime ustar offsets were swapped and are now
  spec-correct (size 124, mtime 136).
- **Promotion** (`promoteAgentBundle`): operator-triggered multipart
  `POST /api/agents` with 201/409/400 mapping (id, conflict, error) —
  the explicit IPC call is the operator gate; nothing uploads
  automatically. **New IPC**: `agent-bundle-promote` (single surface —
  the redundant compile-only channel was removed after the existing
  IPC↔preload consistency guard flagged it, proving the guard works).
- **New module** `src/main/openviking-probe.ts` (row R5): bounded probe of
  an operator-configured OpenViking context DB (default loopback :1933;
  remote https allowed; optional bearer key), session-count inventory,
  401/403 → auth hint. **Interop-only (AGPL-3.0 core — never vendored;
  NOTICE/provenance row required at first ship).** New IPC:
  `openviking-probe`; Tools card "OpenViking (context database)".
- **Boundary preserved**: promotion is one-directional (console →
  workspace); the workspace's own bundles only appear in the R1
  divergence view; no automatic sync.

### Governance relay (P6 — contract row G, final contract phase)

- **New module** `src/main/cubecloud-agent-governance.ts`, grounded in the
  workspace's own approval contract (API.md "Resolve Elicitation
  (URL-based)" + schemas.py `ElicitationRequestEvent`/`Params`):
  - `listPendingElicitations()` — reads the session snapshot's
    `pending_elicitations[]` into an inbox shape (form/url modes, requested
    JSON schema, policy name/phase/content preview, and the mirrored-child
    `target_session_id` routing rule from API.md).
  - `resolveElicitation()` — the **ONE write** the console performs for the
    workspace: the human verdict (`action: accept|decline|cancel` +
    optional form content) delivered to the resource-scoped URL
    `POST /v1/sessions/{sid}/elicitations/{eid}/resolve` (202 accepted;
    404/422 mapped to results). The dedicated URL keeps verdicts out of
    the in-band event channel so policy ASK gates cannot conflate them.
  - `listGovernanceSurfaces()` — the row-R4 view: `/v1/scheduled_tasks` +
    `/v1/policy-registry` + `/v1/sharing` joined tolerantly (older builds
    404 individual surfaces → recorded errors, never throws).
- **New IPC**: `workspace-governance-elicitations`,
  `workspace-governance-resolve` (mirrored-child routing honored:
  delivers to `targetSessionId` when present),
  `workspace-governance-surfaces`; preload + d.ts types.
- **Tools card**: "Workspace governance" — policy count + scheduled-task
  count or unavailable-with-reason states.
- **Mutation-scope guard** shipped in the same commit: a source-level test
  asserting the module contains exactly one POST (the resolve endpoint)
  and zero PUT/DELETE/PATCH — the console stays read-everything except
  where the human verdict flows.
